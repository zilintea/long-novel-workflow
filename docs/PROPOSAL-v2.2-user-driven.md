# 评估提案 v2.2（修正版）— 增加“用户供稿模式”（草案，未实施）

日期：2026-11-24。触发：用户纠正——要改的是“用户可以提交目录、大纲、章节等数据，AI 按用户的思路创作”，原来是 AI 自由发挥。

结论：要改。加一个新模式，不推翻现有模式，做瘦补丁 v2.2。

## 一、先认错：上一版理解错了

上一版把“提交”理解成下游的“提交审稿”（审稿包、批准记录、commit 脚本）。那部分 downstream 确实也缺，但不是用户说的事。

用户说的“提交”在上游：用户先交数据——目录、章节大纲、人物、伏笔、关键情节、甚至草稿章节——AI 再按这份数据创作。上一版没评估这一层。

## 二、现状：技能仓库现在是 AI 自由发挥为主

查了 SKILL.md、docs、templates、scripts，结论如下：

1. 只有两种模式，没有第三种。SKILL.md 第 20–24 行只有 author-gated（AI 提建议、作者批准，proposal-inbox）和 full-auto（AI 全程生成，不填表）。没有“用户供稿”模式：用户交大纲、AI 照着写。
2. 用户只能批准 / 否决，不能供稿。Step 1 是 AI 起草圣经和大纲、作者批准；Step 0 扫榜后才定体裁、标题、人物名，还写明“标题和人物名在扫榜后才定，绝不事先写死”。这套规则默认名字、情节是 AI 定的，用户没有一个入口把自己的名字、章节、情节锁进去。
3. 没有供稿的格式。templates 里只有 bible / outline / chapter_contract / chapter / foreshadowing_ledger 五个模板，全是给 AI 填的。没有 `user_brief`、`user_outline`、`user_characters` 这样的用户提交模板，也没有机器可读的 `outline/chapters.yaml` 模板——SKILL.md 的书目结构里提到了 `chapters.yaml`，但仓库里根本没有它的模板和校验脚本。
4. 没有保真审计。三个检查脚本只审内部一致性：frontmatter 齐不齐、字数够不够、钩子够不够长、伏笔编号存不存在、人物是不是占位名。它们不审“这一章写的是不是用户大纲里那一章”：用户说第 5 章必须发生 X，AI 写成 Y，三个脚本全过，没人拦。
5. 滚动规划会漂移。Step 4 弧线复盘每 30 章按摘要重规划下一弧，没有“用户已冻结的弧不能重规划”的规则。用户交了 80 章大纲，AI 写到第 30 章后可以悄悄把后 50 章改了。
6. Step 5 不是供稿入口。Step 5“导入旧稿”是反方向：已有正文，反推圣经和大纲，再续写。它不处理“只有大纲、还没有正文，用户要 AI 按大纲写”的情况。

对照《时间啊，你慢些走》就很清楚：用户给的是 8 组图 + 一个主题，人物名陆时安、奶奶、苏小满、伏笔 F01–F07、第 1–2 章的情节，全是我定的。如果用户当时交的是自己的大纲（比如第 1 章必须回村、第 2 章必须翻底片、第 3 章必须去木屋），现在这套技能没有地方接这份大纲，只能靠聊天记录口头约束，写着写着就容易走样。

## 三、要加什么：用户供稿模式（User-Driven）

新增第三种模式，和现有两种并列，Step 0 先选模式：全自动 / 作者把关 / 用户供稿。用户供稿模式下，扫榜可选跳过（用户已定体裁和标题，不用 AI 再定）。

### A. 入口：用户能交什么（P0，必须有）

1. 新增 `templates/user_submission/`，三份用户填写模板：
   - `user_brief.md`：一句话主题、基调、视角、字数 / 章数目标、绝对不能写的东西。
   - `user_outline.yaml`：机器可读的目录大纲——卷 / 章号 / 标题 / 必须发生（must_happen）/ 章末钩子 / 欲望 / 出场人物 / 埋 / 兑现的伏笔编号。每章一行，缺章号、重号直接报错。
   - `user_characters.yaml` + `user_foreshadowing.yaml`：人物（名、年龄、标志物、want / flaw）和伏笔（ planted 章、payoff_due 章），有就交，没有就空着，不强制。
2. 新增 `scripts/validate_submission.py`：用户一交数据先校验，不写正文。查：章号连续不重不漏、每章有钩子、每章有 2–4 名出场人物、伏笔编号先登记后使用、人物名在全书一致。校验不过列清单打回，不靠 AI 脑补。
3. 新增 `user_submission/` 目录进书目结构：用户交的原始稿原样存一份（v1、v2……），AI 不改用户原文，只在旁边生成派生文件。用户改大纲要走“修订 + 影响清单”，不悄悄改。

### B. 锁定：用户定的，AI 不能改（P0，必须有）

4. 新增硬规则：用户供稿字段带 `source: user`，锁定（locked）。AI 不能改用户定的章名、章序、必须发生、钩子、人物名、伏笔兑现章；只能在用户留空的地方补，并标 `source: ai-filled`，补的须经用户点头才进正史。
5. 冻结弧：`user_outline.yaml` 里每卷 / 每弧可标 `frozen: true`。Step 4 弧线复盘不得重规划已冻结的弧，只能在冻结的弧内微调写法。
6. 合同改成派生文件，不再是 AI 自由起草：`outline/chapters/NNN.md` 的合同字段（must_happen / hook / characters / foreshadowing）直接从 `user_outline.yaml` 生成，AI 只补 transition 和 desire_payoff 这类执行层字段，且要注明来源。

### C. 保真：写完要对得上用户的大纲（P0，必须有）

7. 新增 `scripts/check_fidelity.py`：对照用户大纲逐章核对——章号和标题对不对、must_happen 的节拍在正文里有没有（节拍清单逐条打勾，缺一条即 FAIL）、出场人物对不对、有没有凭空多出来的主线人物和伏笔、有没有提前兑现用户定在后面的伏笔。三个旧脚本管内部一致，这个新脚本管“是不是按用户写的”。
8. 人工审计加一条：审稿人（AI 复核 + 作者）先对照用户大纲读，再读正文。审稿包里的第一项就是保真对照表，不是先看文笔。

### D. 缺口：缺的只问，不悄悄补（P1）

9. 新增“理解复述”一步：收到用户供稿后，AI 先回一份复述——我理解你的大纲是……、缺这三处关键信息（比如第 12 章只给了标题没有节拍、F03 没写兑现章）、有这两处自相矛盾（比如第 5 章人物已离村、第 8 章又出现在村里）。用户确认或补齐后才开工，不在开工后边写边猜。
10. 缺口分级：标 `must-ask`（章序、必须发生、人物生死、伏笔兑现章——缺了不能写）和 `ai-may-fill`（过渡、景物、次要对话——可先写，审稿时标出来）。现在技能里没有这个区分，所以 AI 遇到缺口要么停住问个没完，要么一声不吭自由发挥。

### E. 变更：用户中途改大纲，要看得见影响（P1）

11. 大纲修订走版本：`user_outline.yaml` 改一版，脚本输出影响清单——哪几章合同要重生成、哪几条伏笔 payoff_due 要挪、哪几章已提交正文会受影响（受影响的已提交章要不要回滚，由用户定，不自动改）。
12. MCP 对齐：在 MCP 的工具里加 `submitUserOutline` / `validateSubmission` / `checkFidelity`，和 Python 脚本同一套规则，避免两条路又分叉。

### F. 下游（上一版 P0，降级为 P1，本次不先做）

13. 上一版提的审稿包、批准记录、commit / rollback 脚本，仍有价值，但它们是“写完怎么交”，不是“按谁的思路写”。等用户供稿模式跑通一章后再补，不在本批先做，避免一次改太多。

## 四、不做的事

- 不删全自动和作者把关模式。用户不交大纲时，现有流程照走。
- 不把用户大纲当成不可讨论的圣旨：校验发现自相矛盾、缺关键信息时，AI 必须先报出来，不硬写。
- 不扩大体裁和平台。v2.2 只加供稿模式，不加新体裁。

## 五、实施顺序（建议）

先做 A + B + C（入口模板、校验脚本、锁定规则、保真脚本），拿《时间啊，你慢些走》第 3 章当首测：把第 3 章合同改成从一份用户大纲派生，写完跑 `check_fidelity.py`，看它能不能抓住“没按大纲写”的情况。A / B / C 跑通后再做 D + E。改完先在 `examples/sample-book/` 上跑回归，三旧脚本必须全过，CHANGELOG 记一笔，再推 GitHub。
