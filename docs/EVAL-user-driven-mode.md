# 评估：技能仓库是否要加“用户供稿模式”（独立评估，不针对任何一本书）

对象：`long-novel-workflow` v2.1.0（`SKILL.md`、`skill.yaml`、`templates/`、`scripts/`、`docs/`、MCP Server）。
问题：用户能否提交自己整理的目录、大纲、章节等数据，AI 按用户的思路创作，而不是 AI 自由发挥？
结论：**要改。加一个新模式，做瘦补丁 v2.2，不重写技能。**

## 一、现状诊断：现在是 AI 自由发挥为主

### 1. 模式只有两种，没有第三种

`SKILL.md` 第 20–24 行、`skill.yaml` 的 description 只写了两种执行方式：

- author-gated：AI 提建议，作者批准后进正史（proposal-inbox 模式）；
- full-auto：AI 全程生成，不强制人工填表。

没有“用户供稿”模式：用户先交数据，AI 照着写。Step 0–Step 6 的 7 个步骤里，也没有哪一步是“接收用户供稿”。

### 2. Step 0 和 Step 1 默认情节是 AI 定的

- Step 0（扫榜）：先扫榜，再定体裁、钩子、标题方向；标题和人物名在扫榜后才定，“绝不事先写死”。
- Step 1（Gate 1）：AI 起草圣经和大纲，作者批准，或全自动直接提交。

这两步都没有用户供稿的入口。用户想交自己的标题、人物名、章节情节，没有地方放，只能靠聊天口头说，写着写着就容易走样。

### 3. 没有供稿的格式，也没有校验

`templates/` 只有 5 个模板，全是给 AI 填的：`bible_template.md`、`outline_template.md`、`chapter_contract.md`、`chapter_template.md`、`foreshadowing_ledger.md`。

缺失：

- 没有用户填写的 `user_brief`（一句话、基调、禁区）；
- 没有机器可读的 `user_outline.yaml`（卷 / 章号 / 标题 / 必须发生 / 钩子 / 人物 / 伏笔）；
- 没有用户人物表、用户伏笔表的提交模板；
- `SKILL.md` 的书目结构里提到了 `outline/chapters.yaml`，但仓库里没有它的模板，也没有校验它的脚本。

用户交来的数据可以是四种完整度：一句话、粗纲、细纲、章节草稿。现在技能不区分这四种，也没有“缺什么、能不能开工”的判定。

### 4. 没有锁定：用户定的东西，AI 可以改

全仓库 grep `source:` / `locked` / `frozen`，除“出场后人物设定锁定”这一条外，没有结果。也就是说：

- 用户定的章名、章序、必须发生、钩子、人物名、伏笔兑现章，没有 `source: user` 标记，没有锁定规则；
- Step 4 弧线复盘每 30 章按摘要重规划下一弧，没有“已冻结的弧不能重规划”的规则；
- 合同是 AI 自由起草的，不是我们从用户大纲派生的。

### 5. 没有保真审计：写偏了没人拦

三个检查脚本只审内部一致性：

- `check_chapter.py`：frontmatter 齐不齐、字数够不够、禁词有没有；
- `check_hooks.py`：钩子够不够长、欲望是不是 8 个里的、兑现节奏对不对；
- `check_continuity.py`：伏笔编号存不存在、knows 清单对不对、人物是不是占位名。

它们都不审“这一章写的是不是用户大纲里那一章”。用户说某章必须发生 X，AI 写成 Y，三个脚本全过。`must_happen` 在合同里只要求“非空”，不要求正文逐条兑现。

### 6. Step 5 不是供稿入口，双轨还分裂

- Step 5“导入旧稿”是反方向：已有正文，反推圣经和大纲，再续写。它不处理“只有大纲、还没有正文，按大纲写”的情况。
- MCP Server 那条路有 `commitChapter` / `rollbackChapter` / `auditChapter`，Python 这条路没有对应的提交 / 回滚脚本；但两条路都没有“提交用户大纲”的工具。工具清单里有建书、读章、起草合同、存草稿、审计、提交、回滚、伏笔管理、结尾规划、改目标、导出续集种子，唯独没有供稿入口。

## 二、要加什么

新增第三种模式“用户供稿模式”（User-Driven），和现有两种并列。Step 0 先选模式：全自动 / 作者把关 / 用户供稿。用户供稿模式下，扫榜可选跳过（用户已定体裁和标题）。

### P0 — 必须有：入口、锁定、保真

1. **供稿模板（`templates/user_submission/`）**：`user_brief.md`、`user_outline.yaml`、`user_characters.yaml`、`user_foreshadowing.yaml`。`user_outline.yaml` 是核心：每章一行，字段为章号、标题、必须发生、章末钩子、欲望、出场人物、埋 / 兑现的伏笔编号、来源标记。
2. **校验脚本 `scripts/validate_submission.py`**：交稿先校验，不写正文。查章号连续不重不漏、每章有钩子、每章出场 2–4 名人物、伏笔先登记后使用、人物名全书一致。校验不过列清单打回。
3. **锁定规则（新增硬规则）**：用户供稿字段标 `source: user`，锁定。AI 不能改用户定的章名、章序、必须发生、钩子、人物名、伏笔兑现章；只能在用户留空处补，标 `source: ai-filled`，补的须经用户点头才进正史。
4. **合同派生**：`outline/chapters/NNN.md` 的合同字段（must_happen / hook / characters / foreshadowing）从 `user_outline.yaml` 生成，AI 只补 transition、desire_payoff 这类执行层字段，并注明来源。
5. **保真脚本 `scripts/check_fidelity.py`**：逐章对照用户大纲核对——章号标题对不对、must_happen 节拍在正文里有没有（逐条打勾，缺一条即 FAIL）、出场人物对不对、有没有凭空多出的主线人物和伏笔、有没有提前兑现用户定在后面的伏笔。
6. **冻结弧**：大纲里每卷 / 每弧可标 `frozen: true`。Step 4 不得重规划已冻结的弧。

### P1 — 应该有：缺口、变更

7. **理解复述**：收到供稿后，AI 先回一份复述——我理解你的大纲是……、缺这几处关键信息、有这几处自相矛盾。用户确认或补齐后才开工，不在开工后边写边猜。
8. **缺口分级**：`must-ask`（章序、必须发生、人物生死、伏笔兑现章，缺了不能写）与 `ai-may-fill`（过渡、景物、次要对话，可先写，审稿时标出来）。现在技能没有这个区分，所以 AI 遇到缺口要么停住问个没完，要么一声不吭自由发挥。
9. **大纲版本与影响清单**：用户改大纲走版本（v1、v2……），原稿原样保存；脚本输出影响清单——哪几章合同要重生成、哪几条伏笔兑现章要挪、哪几章已提交正文会受影响。受影响的已提交章是否回滚，由用户定，不自动改。
10. **合同一致性脚本 `scripts/check_contract.py`**：校验合同与正文 frontmatter 字段一致，并校验上一章钩子在下一章合同里是否交代（硬规则 11 机器化）。

### P2 — 可以有：对齐与效率

11. **MCP 对齐**：在 MCP 工具里加 `submitUserOutline` / `validateSubmission` / `checkFidelity`，与 Python 脚本同一套规则，避免两条路又分叉。
12. **节拍字数预算**：合同里每个 must_happen 节拍给一个字数预算，提交前先算预算，写不够在动笔前就知道。
13. **供稿完整度分级**：一句话 / 粗纲 / 细纲 / 章节草稿四档，每档对应不同的开工程序和追问清单，不是一刀切。

## 三、不改什么

- 不删全自动和作者把关模式。用户不交大纲时，现有流程照走。
- 不动核心规则：文件即真相、钩子 + 欲望阻断、knows 清单、伏笔台账、只改错段、盲写、Gate 3。
- 不把用户大纲当成不可讨论的圣旨：校验发现自相矛盾、缺关键信息时，AI 必须先报出来，不硬写。
- 不扩大体裁和平台。v2.2 只加供稿模式。

## 四、实施顺序与验收

1. 先做 P0（模板、校验、锁定、合同派生、保真脚本、冻结弧），用一份用户大纲跑 3 章当首测。
2. 首测验收：`check_fidelity.py` 能抓住“没按大纲写”的偏离（故意写偏一章，看它是否 FAIL）；三旧脚本在 `examples/sample-book/` 上回归全过。
3. P0 稳了再做 P1；P2 看 P0、P1 的反馈再定。
4. 改完记 CHANGELOG，推 GitHub，版本号 v2.2。

## 五、风险

- 过度锁定会卡住创作：用户大纲本身有漏洞时，锁定会放大漏洞。对策是 P1 的理解复述和缺口分级，先报问题再开工。
- 用户大纲完整度不一：只给标题的大纲和给了逐章节拍的大纲，不能用同一套开工程序。对策是 P2 的四档分级。
- 两条路（Python 与 MCP）再次分叉：对策是 P2 的同一套规则，脚本与工具共用同一份判定逻辑。
